# MSSP 的下一步：AI 驅動階層有限狀態機與 RDR 具現化派發的整合架構

## 摘要

本文的起點是一個容易被誤解的資料夾名稱——「無限維閉包理論」。這個名稱本身是誇大修辭，不是本文的實際主張；它指向的是作者理論上的長期方向（一種類無限多維函數閉包、搭配連續函數呼叫的計算形態），但本文要處理的是這個方向在**當下**、在 CompilableWorld Runtime 這個具體專案裡，真正可以被定義、被檢驗的那一步。

這一步的核心主張，是作者自己的表述：這其實就是 **MSSP 的下一步**。具體來說：

> 使用 AI 撰寫人類幾乎不可能手寫的、更複雜的有限狀態機，大量套用在模組上，並依 **宏（macro）／中（meso）／微（micro）** 三層持續分類與交互；這麼做同時是為了**計算效率**與**遊戲／世界複雜度**兩個目的；而不管產生的程式碼多複雜，MSSP 的概念加上 AI，應該讓整體維持**可控**。

這句話裡有三個獨立的技術問題，過去分散在三份不同文件中，從未被放在一起看：

1. **複雜度從哪裡來、分幾層** —— 已由 [`05-hierarchical-state-machine-mud.md`](05-hierarchical-state-machine-mud.md) 定義（世界／區域／場景／實體／系統／行為六層狀態機），但該文件假設轉移規則本身是可手寫的。
2. **誰執行這些規則、如何保持模組邊界** —— 已由 [`07-evennia-to-mssp-runtime.md`](07-evennia-to-mssp-runtime.md) 定義（World Kernel、Module Contract、Event Bus），但該文件沒有處理「規則數量與規則間耦合大到需要派發層」的情況。
3. **當規則多到人類寫不出來、AI 寫出來之後，系統還能不能被認識與信任** —— 這是全新的一塊，來源是作者私人研究資料夾中的 RDR（Reified Dispatch Runtime）方法論與 MSSP×RDR 整合規格書，目前完全沒有進入 CompilableWorld 系列文件。

本文不重寫 05 與 07 已經定義好的形式化內容，只做三件事：（a）把「宏中微」精確對齊到 05 既有的六層狀態機，而不是發明新分類；（b）指出 07 的 Kernel 目前**沒有**、但一旦 AI 大量生成規則就會需要的派發／快取／拆環機制，並說明為何這正是 RDR 的 L3／L4；（c）用 MSSP×RDR 整合規格書已經修正過的核心公理，精確定義「可控」在這裡到底是什麼意思——不是人類能追蹤每一條軌跡，而是結構保持可認識、動態保持可觀測。

本文是架構提案，不是實作紀錄。第七章會誠實列出目前完全沒有驗證過的部分。

# 第一章　問題：複雜度的來源不只是狀態空間，還有規則本身

## 1.1 05 已經解決的問題

`05-hierarchical-state-machine-mud.md` 第二章已經證明：把整個世界所有狀態直接組合成單一巨型 FSM 會發生狀態爆炸（一個角色的姿態×心理×戰鬥×社會×任務×位置×法律狀態組合就有 2,880 萬種），因此正確作法是把世界拆成

$$
\mathcal{M} = \{ M_{\mathrm{world}}, M_{\mathrm{region}}, M_{\mathrm{scene}}, M_{\mathrm{entity}}, M_{\mathrm{system}}, M_{\mathrm{action}} \}
$$

六層獨立、透過事件協作的狀態機。這解決了**狀態空間**的爆炸。

## 1.2 05 沒有處理的問題

05 第七章定義的轉移規則形式是

$$
r:(S,A,C)\rightarrow(S',E,O)
$$

並在附錄舉的例子（`unlock_door_with_key`）是一條人類幾秒鐘就能寫完的規則。整份文件隱含假設：規則的**數量**與**內部邏輯複雜度**是可控的，真正的挑戰在狀態分類。

但作者現在指出的是另一件事：當世界規模拉大到宏（世界／區域級的政治、經濟、氣候、勢力消長）、中（場景／系統級的任務網、派系關係、聲望連動）、微（實體／行為級的個別 NPC 行為樹、戰鬥細節）都要同時填滿內容時，**規則本身**——不是狀態空間，是轉移規則、行為樹、事件反應鏈的集合——會膨脹到人類作者無法一條條手寫、卻仍然需要相互一致、可測試、可維運的程度。

這不是 05 的缺陷，是 05 刻意沒有處理的下一層問題。作者的判斷是：這一層的解法是讓 AI 來寫這些規則，而不是繼續要求人類手寫。

## 1.3 新問題的精確表述

> 當轉移規則的作者從人類變成 AI，且規則數量因此可以大量擴張時，系統要如何同時保持（a）計算上可執行、（b）內容上夠複雜足以撐起世界豐富度、（c）對人類維護者而言仍然可控？

這三個子問題分別對應本文第三、第四章的 RDR 與 MSSP 兩條線。

# 第二章　宏／中／微：對齊既有六層狀態機，而不是新分類

作者用「宏、中、微」描述分類方式，這裡明確主張：**這不是要在 05 的六層之外另建一套分類，是同一套六層的三段式歸並**，理由是 05 的六層本來就有天然的粒度差異：

```text
宏 Macro  ── M_world, M_region        世界／區域級規則
中 Meso   ── M_scene,  M_system       場景／系統級規則（任務網、派系、經濟）
微 Micro  ── M_entity, M_action       個別實體／單次行為級規則
```

這個歸並不是裝飾性的重新命名，它有實際作用：**AI 生成規則時，宏中微決定了規則的作用範圍與生成策略應該不同。**

- **宏層規則**：數量少、影響面大、變化慢（世界紀元、氣候相位、戰爭態勢）。適合人類審核每一條，AI 提案、人類核准。
- **中層規則**：數量中等、彼此高度耦合（派系聲望連動任務可用性、經濟連動治安）。這是耦合與循環依賴最容易出現的一層——例如「治安」是「巡邏 NPC 密度」的函數，而「巡邏 NPC 密度」又受「治安預算」影響，「治安預算」又受「治安」本身回饋——這正是第四章要談的 SCC（強連通分量）拆環問題發生的地方。
- **微層規則**：數量龐大（每個 NPC、每種道具互動、每個戰鬥招式），單條規則簡單但總量驚人。這是 AI 生成規則、人類完全無法逐條審核的典型情況，也是最需要 Island Test（07 §5.5）與 Module Contract 邊界的一層——人類不審核規則內容，只審核模組的讀寫權限邊界。

換句話說：**宏中微不只是空間層級，是「AI 自主權遞增、人類審核粒度遞減、但結構邊界要求遞增」的三段管理策略**。宏層人類看內容，微層人類只看邊界，中層是兩者都要、也是最需要新機制的一層。

# 第三章　為什麼是 RDR：計算效率與世界複雜度是同一個問題

作者原話：「我是同時為了計算效率跟遊戲複雜度（世界）」。這句話容易被讀成兩個要權衡的目標（效率 vs. 複雜度，通常互斥），但作者研究資料夾中的 RDR 方法論給出的其實是**同一個機制解決兩者**的論證：只要規則之間存在大量重疊子問題（同一條聲望規則被上千個 NPC 共用、同一條天氣影響規則被整個區域的實體共用），豐富度（規則數量、覆蓋率）與效率（重複計算的次數）就不是互斥的兩端，而是「有沒有把重複計算的部分具現化並快取」這一件事的兩面。

## 3.1 RDR 的五層，映射到 CompilableWorld Runtime 現況

RDR 定義五層：L1 純定義、L2 宣告式呼叫、L3 派發／快取咽喉、L4 圖排程與拆環、L5 自適應閘門。逐層對照現有的 `07-evennia-to-mssp-runtime.md` 架構與 `src/compilableworld/` 現有實作：

| RDR 層 | RDR 要求 | CompilableWorld Runtime 現況 |
|---|---|---|
| L1 純定義 | 引用透明，無 I/O、無隱藏狀態 | **已經是不變量**——`AGENTS.md` 第 3 條「TMS 模組只能回傳 `StateDelta` 與 `EventIR`，由 Kernel 原子提交」本質上就是 L1 純度要求，只是當初沒有用 RDR 的語彙命名 |
| L2 宣告式呼叫 | 以名稱引用能力，不直接呼叫函數 | **已經是 Action IR**——05 §5.2 的 $(\alpha, v, \tau, \iota, \mu, \theta, \pi, \kappa, \epsilon, \phi)$ 元組就是宣告式呼叫的具體格式 |
| L3 派發／快取咽喉 | 攔截每次呼叫，集中做去重與 memoization | **目前不存在**——07 §4.4 的 Action Runtime 與 §4.5 的 Transition Engine 是直接呼叫模組、直接產生 Delta，沒有一個「所有呼叫都會經過」的單一咽喉點做快取 |
| L4 圖排程／SCC 拆環 | 呼叫結構是圖而非樹時，用強連通分量縮合斷環 | **目前不存在，且目前的 Event Bus 無法替代**——Event Bus（07 §4.6）解決的是「模組不直接呼叫彼此」，但不解決「衍生值之間的循環依賴」（見 3.2） |
| L5 自適應閘門 | 觀察重用率、決定要不要啟用整套機制 | **目前不存在，但這是刻意的**——見 3.3，這其實是保護現有極簡 Kernel 設計的機制，不是額外負擔 |

## 3.2 為什麼 Event Bus 不夠：衍生值循環是真實存在的問題

07 §4.6 已經正確地規定模組間不直接呼叫彼此、只能透過事件協作。但事件協作解決的是「執行順序」與「直接耦合」，不解決**衍生值（derived value）之間的循環依賴**。

用第二章舉的中層例子：

```text
治安(security) = f(巡邏密度)
巡邏密度(patrol_density) = g(治安預算)
治安預算(security_budget) = h(治安, 稅收)
```

`治安` 依賴 `巡邏密度`，`巡邏密度` 依賴 `治安預算`，`治安預算` 又依賴 `治安` 本身。這是一個真實的環，不是設計錯誤——真實世界的治安/預算/巡邏就是互相回饋的。用事件鏈天真地重算（`治安變動 → 觸發預算重算 → 觸發巡邏重算 → 觸發治安重算 → …`）會不終止，或者需要人工加上「最多重算 N 輪」這種不精確的 hack。

RDR 的 L4 給出的正確作法不是「修排程器」，是先確認度量在環上是否良定義（RDR 原文：「度量良定義性先於演算法」）。以這個例子而言，正確的度量不是「治安的絕對值」（在環上會發散或震盪），而是換成類似「可達集基底和，每節點計一次」這種在環上依然收斂的形式——這正是 L4 用 Tarjan SCC 縮合強連通分量、把環當成一個整體節點求值一次的原因。

**這一點目前完全不存在於 CompilableWorld Runtime 的設計中**，因為到目前為止（`gray_crown`、`mingyun_zhiyu_peace_city` 兩個範例世界）都還沒有出現衍生值循環——這正是為什麼作者現在提出這個問題，而不是這個問題早就該被發現：**規模還小的時候，環不會出現；一旦 AI 大量生成中層規則，環幾乎必然出現。**

## 3.3 L5 閘門：為什麼不是「把整個 Kernel 重寫成 RDR」

RDR 方法論明確警告：RDR 不適用於低重用、一次性、或呼叫本身很便宜的負載——套用在不需要的地方，派發間接的開銷會吃掉收益。這對應到 L5 的角色：**决定這整套機制在特定模組上是否值得啟用**。

具體到本專案：`examples/gray_crown`（3 個房間的示範世界）完全不需要 L3/L4；`examples/mingyun_zhiyu_peace_city`（5 個房間、8 模組的真實內容切片）目前也不需要——因為還沒有大到出現重疊子問題或衍生值循環。**L3/L4 應該是可選、按模組啟用的機制，不是 Kernel 的預設路徑。** 這與 07 §16.1「Kernel 內建所有玩法會變成新的單體引擎」的反模式警告是同一個精神：不要為了應付未來可能的規模，現在就把所有模組都套上派發層。

# 第四章　為什麼是 MSSP：把「可控」精確定義成兩個可證偽的判據

作者的原話「不管程式碼在複雜，利用 MSSP 概念，還有 AI，應該是可控的」，如果不加定義，「可控」會變成一句空話——正是 MSSP×RDR 整合規格書要處理的問題：原始 MSSP 公理「畫不出來就是設計失敗」，被修正為區分**結構可認識性**與**軌跡可預測性**兩件事，而只有前者是設計判準。

## 4.1 判據一：結構可認識性（人類/AI 維護者能不能看懂「這是什麼、能做什麼」）

不要求追蹤 AI 生成的某條微層規則在第 10,000 次執行時會做什麼——那是軌跡，本來就不保證可預測。要求的是：**任何時候，維護者都能不看規則內容，只看契約，就知道這個模組被允許讀什麼、寫什麼、發出什麼事件。**

這件事在 CompilableWorld Runtime 裡已經有現成的載體，不需要新發明：

- 07 §5.3 的 **Module Contract**（`requires` / `provides.states` / `provides.actions` / `provides.events` / `permissions.read` / `permissions.write`）就是判據一的具體格式。
- 07 §5.5 的 **Island Test**（每個 TMS 應能在 Minimal Kernel + Mock Entity + Mock State + Mock Event Bus 下獨立測試）就是判據一的可驗證形式——如果一個模組必須啟動其他模組才能測試，代表存在隱藏耦合，代表結構不可認識。

也就是說：**AI 生成微層規則時，不需要每條規則都被人類讀懂，但生成規則所屬的模組必須先有一份人類寫（或人類審核過）的 Module Contract，而且必須通過 Island Test。** 這把「審核 AI 生成的內容」這個不可擴展的工作，換成「審核 AI 生成內容所在的邊界」這個可擴展的工作。

## 4.2 判據二：動態可觀測性（系統當下的行為能不能被即時認出）

判據一管的是設計時；判據二管的是運行時——**不要求預知 AI 生成的規則會怎麼演變，但要求任何時刻都能被儀表化、被即時認出目前處於什麼régime。**

這對應 07 §10 已經定義、但目前 `src/compilableworld/` 尚未實作完整的 **DMS（觀測與維運）**：Entity Count、Action Throughput、Event Throughput、Module Errors、State Conflict、Scheduler Lag。一旦 AI 大量生成規則，這些指標的重要性會從「不錯的附加功能」變成「唯一能知道系統健不健康的方式」——因為人類已經不可能靠讀規則內容判斷。

## 4.3 「可控」的精確定義

綜合以上，本文對「可控」給出一個可證偽的定義，取代作者原話裡的直覺說法：

> 一個由 AI 生成大量複雜規則的 CompilableWorld 模組，稱為可控，若且唯若：（1）它有一份人類審核過的 Module Contract，且通過 Island Test；（2）它的運行狀態可透過 DMS 指標即時觀測，且指標維持在事先宣告的正常範圍內。

失敗判準明確對稱：**任一條件不成立即為失敗**——契約含糊或未過孤島測試（結構不可認識），或者沒有觀測手段、出了問題也不會被發現（動態不可觀）。這個定義刻意不要求「人類能理解每條規則」，因為那個要求本來就會在 AI 生成規則的規模下必然失敗，用它當判準只會導致要嘛拒絕使用 AI 生成，要嘛把判準悄悄棄守。

# 第五章　具體提案（尚未實作，供下一階段參考）

以下是本文對 Kernel／Module 系統的修改建議，刻意保持最小、且明確標記優先序，不是一次性大改。

## 5.1 優先度最高：把判據一做實——Module Contract 需要一個「AI 生成規則集」的宣告欄位

目前 07 附錄 A 的 Module Contract 格式（`requires` / `provides` / `permissions`）沒有欄位說明「這個模組的規則內容是人類手寫還是 AI 生成、生成後有沒有人類審核過」。建議新增：

```yaml
module:
  id: faction.reputation
  version: 0.1.0
  layer: TMS
  tier: meso          # macro | meso | micro，對應第二章的歸並

authoring:
  rule_origin: ai_generated   # human_authored | ai_generated | ai_generated_reviewed
  reviewed_by: null           # 人類審核者，ai_generated_reviewed 時必填
  rule_count: 340
```

這不是執行期機制，是 Authoring Layer 的宣告——延續 `AGENTS.md` 第 7 條「新資料欄位需先修改 Authoring Schema／Compiler，再修改 Runtime」的既有原則，不在執行期偷加欄位。

## 5.2 優先度次高：Transition Engine 加一個可選的派發／快取層（僅對宣告 `tier: meso` 或 `tier: macro` 且 `rule_origin` 非 `human_authored` 的模組啟用）

對應 RDR L3。實作範圍限定在：同一條轉移規則、同一個狀態快照（`(rule_id, relevant_state_hash)`）在同一 tick 內被多個實體觸發時，只計算一次。這是 memoization 的最小形式，不涉及排程或拆環，風險低、效益直接對應「大量 NPC 共用同一條規則」的情境。

## 5.3 優先度中：SCC 偵測工具，僅用於中層規則的建構期檢查

不是執行期排程器改寫，是 Compiler（07 §8.3 的 `compile_world()` 流程）在編譯期對衍生值的依賴圖跑一次 Tarjan SCC，若偵測到環，**編譯失敗並報告環的路徑**——強迫作者（或 AI）在編譯期就換成環上良定義的度量（3.2 節的可達集基底和），而不是留到執行期才發現不終止。這比在 Transition Engine 裡即時拆環風險小得多，且與現有 `build-report.json` 的驗證哲學（07 §8.3、既有 `compiler.py` 的 required-field/unique-id/reachability 檢查）完全一致。

## 5.4 優先度最低、明確不建議現在做：L4 執行期圖排程、L5 自適應閘門

這兩層只有在 5.3 的編譯期 SCC 檢查已經證明「環在真實內容裡頻繁出現、且無法靠換度量在編譯期解決」之後才有必要——目前兩個範例世界都還沒有觸發這個情況。提前做，違反 07 §16.1 的反模式警告。

# 第七章　誠實限制（本文尚未驗證的部分）

比照 MSSP×RDR 整合規格書自身的「誠實限制」章節精神，明列本文尚未證明的部分，避免這份文件被誤讀成已驗證的架構：

1. **第三章的衍生值循環例子（治安/巡邏/預算）是假設性的，不是從真實內容中觀察到的。** 目前 `mingyun_zhiyu_peace_city` 範例世界規模太小，尚未真的出現過這種環。這個問題目前是理論推演，不是實測發現。
2. **第五章的所有提案都沒有寫過一行程式碼，也沒有評估過對現有 7 個單元測試與既有兩個範例世界的相容性影響。**
3. **判據一、判據二的「可控」定義是本文的產物，不是作者原話的逐字轉譯**——是把作者口語化的「應該是可控的」轉成可證偽形式的嘗試，這個轉譯本身可能與作者實際想法有落差，需要作者確認。
4. **AI 大量生成規則後，誰、用什麼流程審核 Module Contract、誰批准 `rule_origin: ai_generated_reviewed`，本文完全沒有定義**——07 §9.2 提過 World Builder Agent / Rule Agent / Reviewer Agent 的分工構想，但那是概念性的角色列表，不是可執行的審核流程。
5. **RDR 方法論原文明確指出它不是通用範式，出了「高重用、純函數、優化可分離」的包絡就會退化成開銷或風險**——本文第三章的映射，前提是 CompilableWorld 的規則集確實會落在這個包絡內（大量 NPC 共用少量規則）。如果實際情況是規則彼此高度異質、重用率低，RDR 這條線可能整個不適用，屆時應該直接放棄，而不是勉強套用。
